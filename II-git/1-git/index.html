Git

Teil II · Git · ca. 48 Min. · Braucht: Terminal, VS Code

Was ist Git?

Git macht Schnappschüsse deines Projekts. Jeder Schnappschuss (Commit) hat eine Beschreibung. Du kannst sehen, was sich zwischen zwei Schnappschüssen geändert hat, und jeden alten Stand zurückholen.

main   ●────●────●────●        ← jeder Punkt ist ein Commit
             \
experiment    ●────●           ← ein Branch: ausprobieren, ohne main zu gefährden

Die wichtigsten Begriffe

Begriff Bedeutung Claude fragen
Repository Ein Projektordner unter Git-Kontrolle „Mach diesen Ordner zu einem Git-Repository.“
Diff Was genau hat sich geändert? „Zeig mir, was sich seit dem letzten Commit geändert hat.“
Commit Ein gespeicherter Zwischenstand „Committe den aktuellen Stand mit einer passenden Nachricht.“
Branch Eine parallele Version zum Ausprobieren „Leg einen Branch experiment an.“
Zurücksetzen Einen alten Stand wiederherstellen „Mach die letzte Änderung an ideen.md rückgängig.“
.gitignore Dateien, die Git ignorieren soll „Leg eine .gitignore an, die große PDFs und den Ordner tmp/ ausschließt.“

In VS Code siehst du alles auch grafisch: Symbol Quellcodeverwaltung in der linken Leiste.

Übung: Mutig verschlimmbessern

  1. Committe deinen aktuellen Stand.
  2. Bitte Claude: „Schreib ueber-mich.md komplett um, im Stil eines Piraten.“
  3. Sieh dir den Diff an. Gefällt dir das?
  4. Nein? „Stell den Stand vom letzten Commit wieder her.“

Aha: Mit einem verlässlichen Weg zurück kannst du viel mutiger experimentieren.

Branches

Ein Branch (Zweig) ist eine eigene Linie von Commits. Der Hauptzweig heißt meist main. Willst du etwas ausprobieren, zweigst du ab. main bleibt dabei unberührt.

gitGraph
  commit id: "Törnplan v1"
  commit id: "Hafenliste"
  branch experiment
  checkout experiment
  commit id: "Route über Hvar"
  commit id: "Kosten neu"
  checkout main
  commit id: "Tippfehler"
  • Du arbeitest immer auf genau einem Branch. In VS Code steht er unten links.
  • Wechseln geht in Sekunden. Die Dateien im Ordner ändern sich dann passend zum Branch.
  • Ein Branch kostet nichts. Lieber einen zu viel als einen zu wenig.

Claude fragen: „Leg einen Branch route-hvar an und wechsle dorthin.“ · „Auf welchem Branch bin ich?“

Zusammenführen: Merge

Hat sich das Experiment gelohnt, holst du es zurück nach main. Das heißt Merge (zusammenführen). Git übernimmt die Änderungen aus beiden Zweigen in einem neuen Commit.

gitGraph
  commit id: "Törnplan v1"
  commit id: "Hafenliste"
  branch experiment
  checkout experiment
  commit id: "Route über Hvar"
  commit id: "Kosten neu"
  checkout main
  commit id: "Tippfehler"
  merge experiment id: "Merge"

Claude fragen: „Führe den Branch experiment in main zusammen.“

Hat sich das Experiment nicht gelohnt? Dann lässt du den Branch einfach liegen oder löschst ihn. main hat nie etwas davon gemerkt.

Merge-Konflikte

Meistens merged Git alles allein. Nur wenn beide Zweige dieselbe Stelle in derselben Datei geändert haben, weiß Git nicht, welche Version gilt. Das ist ein Merge-Konflikt. Git schreibt dann beide Versionen in die Datei und markiert sie:

Abfahrt am Samstag um
<<<<<<< HEAD
10:00 Uhr ab Split.
=======
08:00 Uhr ab Trogir.
>>>>>>> experiment
  • Oben (bis =======) steht deine Version auf main, unten die aus experiment.
  • Du entscheidest: eine Version behalten, beide kombinieren oder etwas Neues schreiben. Dann die Markierungen löschen und committen.
  • Ein Konflikt ist kein Fehler und nichts geht kaputt. Git fragt nur nach.

Claude fragen: „Es gibt einen Merge-Konflikt. Zeig mir beide Versionen, erklär den Unterschied und schlag eine Lösung vor.“ Entscheiden tust du.

Git-Strategien: Wie Teams Branches nutzen

Wie viele Branches man anlegt und wann man merged, ist Absprache. Drei bekannte Strategien:

Strategie Idee Passt für
Alles auf main Kein Branch, nur Commits. Allein, kleine Projekte, den Workshop
GitHub Flow main ist immer in Ordnung. Für jede Änderung ein kurzer Branch, danach zurück nach main. Allein oder im Team, die meisten Projekte
Git Flow Zwei Dauer-Zweige: main (nur fertige Versionen) und develop (Arbeitsstand). Dazu Feature-Branches. Große Teams mit festen Versionen (v1.0, v2.0)

So sieht Git Flow aus. Auf main landen nur fertige Versionen mit einem Etikett (Tag) wie v1.0:

gitGraph
  commit id: "Start" tag: "v0.1"
  branch develop
  checkout develop
  commit id: "Arbeit 1"
  branch feature-karte
  checkout feature-karte
  commit id: "Karte 1"
  commit id: "Karte 2"
  checkout develop
  commit id: "Arbeit 2"
  branch feature-kosten
  checkout feature-kosten
  commit id: "Kosten 1"
  checkout develop
  merge feature-kosten id: "Kosten fertig"
  checkout main
  merge develop id: "Release" tag: "v0.2"
  checkout feature-karte
  commit id: "Karte 3"
  checkout develop
  merge feature-karte id: "Karte fertig"
  checkout main
  merge develop id: "Release 1.0" tag: "v1.0"

Für dich reicht am Anfang alles auf main und für Experimente ein kurzer Branch (GitHub Flow). Git Flow lohnt sich erst, wenn viele Leute an einem Projekt mit festen Versionen arbeiten.
