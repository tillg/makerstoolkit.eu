2.1 Was ist Git?

Dauer: ca. 5 Min.

Worum geht's

Git macht Schnappschüsse deines Projekts und merkt sich zu jedem, was sich geändert hat. Mit Git kann man jederzeit zu einem früheren Stand zurück. Darum darf die KI große Änderungen machen. Reine Erklärung, keine Übung. Wir wecken hier das Gefühl, dass Mut sich lohnt.

Lernziel

Nach diesem Thema können die Teilnehmenden …

  • in eigenen Worten sagen, was ein Commit ist (ein Schnappschuss mit Beschreibung).
  • erklären, warum Git bei der Arbeit mit einer KI so wichtig ist.
  • Git von Dropbox/Google Docs unterscheiden (bewusst gesichert, nicht automatisch).

So erklären wir es

  1. Das Problem. Alle kennen Hausarbeit_final.docx, Hausarbeit_final_v2.docx, Hausarbeit_final_NEU_wirklich.docx. Wer weiß noch, was in v2 anders war?

    Stell dir vor, du lässt eine KI an deiner Hausarbeit arbeiten. Sie ändert 20 Stellen auf einmal. Gefällt dir nicht. Wie kommst du zurück?

  2. Das Bild: Spielstand speichern. Wie im Videospiel vor dem Endgegner. Du speicherst, wagst etwas, und wenn es schiefgeht, lädst du den Spielstand. Ein Speicherpunkt heißt in Git Commit.

    Ein Commit ist ein Spielstand mit Notiz: „Törn-Route bis Korsika fertig“.

  3. Der Verlauf. Aneinandergereihte Commits sind eine Zeitleiste. An die Tafel/ans Display:
    ●────●────●────●      ← jeder Punkt ist ein Commit, ganz rechts ist heute
    Bergbild für die Merkhilfe: Jeder Commit ist ein Basislager. Du kannst von dort aus einen Gipfelversuch wagen und, wenn das Wetter kippt, zurück ins Lager.
  4. Abgrenzung. Dropbox und Google Docs speichern von selbst, aber ohne Notiz und ohne Überblick. Git speichert nur, wenn du (oder Claude auf deine Bitte) einen Commit machst. Dafür bleibt jeder Stand sauber beschriftet.
  5. Warum jetzt, mit KI? Ein Agent ändert schnell und viel. Ohne Netz traut man sich nicht, ihm viel zu erlauben. Mit Git ist der Preis eines Fehlers: ein Befehl.

    Git ist das Sicherheitsnetz, das aus „vorsichtig fragen“ ein „mutig ausprobieren“ macht.

  6. Offline. Git läuft komplett auf dem eigenen Rechner. Nichts geht ins Internet (das wäre erst 2.9 GitHub).

Zeigen (Live-Demo)

Kurz, höchstens 2 Minuten. Am Demo-Projekt (Segeltörn-Planer) im Terminal:

git log --oneline

Zeigt die Zeitleiste mit Kurznachrichten. Wir lesen 2–3 Einträge laut vor. Alternativ in VS Code die Ansicht Quellcodeverwaltung (linke Leiste) öffnen. Wichtig: Die Teilnehmenden müssen nichts nachtippen.

Selbst machen (Übung)

Keine Übung. Reflexionsfrage in die Runde:

Wann hast du zuletzt eine Datei kaputtgemacht und gewünscht, du könntest zurück? Was hättest du gern gespeichert gehabt?

Stolpersteine & Fragen

  • „Ist Git = GitHub?“ Nein. Git ist das Programm auf deinem Rechner, GitHub ein Online-Dienst dazu. Das kommt erst in 2.9.
  • „Speichert Git automatisch?“ Nein, nur bei einem Commit. Was nicht committet ist, kann Git nicht zurückholen.
  • „Geht das auch mit Word/PDF/Bildern?“ Es geht, aber den Unterschied zwischen zwei Ständen sieht man nur bei Textdateien gut (deshalb Markdown, siehe 1.5).
  • Git nicht installiert? Siehe 1.2. git --version im Terminal prüft es.

2.2 Repository

Dauer: ca. 5 Min.

Worum geht's

Ein Repository ist ein ganz normaler Projektordner, den Git beobachtet. Ein Befehl (oder ein Satz an Claude), und der Ordner hat ein Gedächtnis. Davor einmalig: Git sagen, wer man ist.

Lernziel

Nach diesem Thema können die Teilnehmenden …

  • erklären, was ein Repository ist (Ordner + verstecktes Gedächtnis).
  • Name und E-Mail für Git einrichten.
  • einen Ordner zum Repository machen (selbst oder durch Claude) und prüfen, ob es geklappt hat.

So erklären wir es

  1. Das Bild: Logbuch an Bord. Der Projektordner ist das Boot. Das Repository ist das Logbuch, das im Boot liegt: Es merkt sich Kurs und Ereignisse, ohne dass das Boot sich ändert.

    Alle deine Dateien bleiben, wie sie sind. Git legt nur einen versteckten Ordner .git daneben. Das ist das Logbuch. Löschst du ihn, ist das Projekt wieder ein normaler Ordner, nur ohne Gedächtnis.

  2. Zwei Schritte, einmal pro Computer bzw. Projekt:
    • Vorstellen (einmal pro Computer): Git schreibt bei jedem Commit den Autor dazu. Darum muss es Name und E-Mail kennen. Ohne das bricht der erste Commit mit einer Fehlermeldung ab.
    • Anlegen (einmal pro Projekt): git init im Projektordner.
  3. Wo? Im Ordner, den wir in 1.4 in VS Code geöffnet haben. Nicht im Home-Verzeichnis, nicht auf dem Desktop selbst, sondern in dem einen Projektordner. Genau dieser Ordner ist später auch der Ort für die Wissensbasis (Teil III).
  4. Zwei Wege. Selbst im Terminal oder Claude bitten. Wir zeigen beides: Der Befehl ist kurz, aber „Mach diesen Ordner zu einem Git-Repository“ geht genauso.

Zeigen (Live-Demo)

Neuer leerer Ordner segeltoern-planer, in VS Code geöffnet:

git config --global user.name "Dein Name"
git config --global user.email "du@beispiel.de"
git init
git status

git status ist der Kontrollblick: Es soll antworten, dass es noch nichts zu committen gibt (bzw. neue, nicht beobachtete Dateien auflistet). Dann in VS Code auf die Quellcodeverwaltung zeigen: Vorher gab es die Schaltfläche „Repository initialisieren“, jetzt ist die Ansicht leer und bereit. Danach das Gleiche mit Claude zeigen (in einem zweiten Ordner):

Mach diesen Ordner zu einem Git-Repository und sag mir, ob es geklappt hat.

Im Manual-Modus (so haben wir es in 1.4 eingestellt) fragt Claude vor dem Ausführen um Erlaubnis (1.7 Berechtigungen). Das ist gut so. Im Auto-Modus entscheidet stattdessen das Prüfmodell, dann kommt keine Abfrage.

Selbst machen (Übung)

  1. Falls noch nicht geschehen: Name und E-Mail setzen (die Befehle oben, mit eigenen Angaben).
  2. Im eigenen Projektordner:
    Mach diesen Ordner zu einem Git-Repository und zeig mir danach den Status.
  3. Geklappt, wenn der Status ohne Fehler erscheint und im Ordner (mit „versteckte Dateien anzeigen“) ein .git liegt.

Stolpersteine & Fragen

  • E-Mail-Adresse: Muss keine echte sein, aber sie landet im Verlauf. Wer später auf GitHub veröffentlicht, nimmt besser die dort angebotene anonyme Adresse (vor dem Workshop prüfen, ob wir das ansprechen). Datenschutz: O.1.
  • Fehlermeldung „Please tell me who you are“: Name/E-Mail fehlen noch. Befehle oben ausführen.
  • git: command not found / Windows: Git ist nicht installiert oder das Terminal wurde nach der Installation nicht neu gestartet (1.2).
  • Falscher Ordner: git init im Home-Ordner macht alles darin zum Repository. Vorher mit pwd (Mac) bzw. in VS Code oben im Terminal prüfen, wo man ist.
  • Branch heißt master statt main: Git nutzt standardmäßig weiter master, bis Git 3.0 main einführt (Stand 2026-11, [KB] 24, §Branches, HEAD, tags). Wir stellen deshalb git config --global init.defaultBranch main ein (schon in 1.2). Wer das vergessen hat: Befehl nachholen. Für Teilnehmende ist es sonst egal, wir sagen es nur, falls jemand fragt.
  • Nicht in Dropbox/iCloud anlegen: Sync kann .git beschädigen, siehe O.4.

2.3 Änderungen & Diffs

Dauer: ca. 5 Min.

Worum geht's

Ein Diff zeigt Zeile für Zeile, was sich gegenüber dem letzten Stand geändert hat: rot raus, grün rein. Wer Diffs lesen kann, kann der KI Änderungen anvertrauen und trotzdem die Kontrolle behalten.

Lernziel

Nach diesem Thema können die Teilnehmenden …

  • einen Diff lesen (rot = entfernt, grün = neu).
  • den Diff in VS Code öffnen oder Claude danach fragen.
  • an einem Diff entscheiden, ob sie die Änderung behalten wollen.

So erklären wir es

  1. Das Bild: Korrekturmodus. Wie „Änderungen nachverfolgen“ in Word oder wie ein Mathelehrer, der eine Rechnung korrigiert: Durchgestrichenes, daneben das Neue. Nur ohne dass jemand die Datei „final“ nennen muss.
  2. Lesen lernen. Beispiel aus der Mathematik:
    - Die Summe der Winkel im Dreieck beträgt 360°.
+ Die Summe der Winkel im Dreieck beträgt 180°.

    Rot mit Minus: stand vorher da, ist jetzt weg. Grün mit Plus: ist neu. Unveränderte Zeilen drumherum geben dir den Zusammenhang.

  3. Wozu? Claude schreibt schnell und viel. Du musst nicht alles lesen, aber du solltest sehen, was es angefasst hat. Ein Diff ist die Quittung.

    Frag dich beim Diff: Hat Claude nur das geändert, worum ich gebeten habe? Oder auch etwas, das ich nicht wollte?

  4. Voraussetzung: ein Stand zum Vergleichen. Git vergleicht mit dem letzten Commit. Gab es noch keinen, ist alles „neu“. Darum kommt gleich danach 2.4 Commits. Für die Demo brauchen wir mindestens einen Commit vorab.
  5. Zwei Wege zum Diff: VS Code (Quellcodeverwaltung, Datei anklicken, links alt, rechts neu) oder Claude fragen.

Zeigen (Live-Demo)

Vorbereitung (vor dem Workshop): Demo-Ordner mit toernplan.md und einem Commit. Dann:

Ergänze in toernplan.md einen Abschnitt „Wetter-Alternativen“ mit drei Ideen, falls der Wind zu stark ist. Ändere sonst nichts.

Danach in VS Code auf Quellcodeverwaltung: Die Datei erscheint mit einem „M“ (modified). Anklicken, die Zwei-Spalten-Ansicht zeigen. Alternativ im Terminal git diff. Dann Claude fragen:

Zeig mir, was sich seit dem letzten Commit geändert hat, und fasse es in drei Sätzen zusammen.

Wir weisen darauf hin, dass der Satz „Ändere sonst nichts“ im Prompt den Diff klein hält.

Selbst machen (Übung)

  1. Bitte Claude, in einem eigenen Dokument einen Absatz zu ergänzen und einen anderen umzuformulieren.
  2. Öffne den Diff in VS Code.
  3. Beantworte für dich: Was ist neu, was weg? Wäre ich auch ohne Diff darauf gekommen?
  4. Geklappt, wenn du die rote und die grüne Zeile zu deiner Bitte zuordnen kannst.

Stolpersteine & Fragen

  • Kein Diff sichtbar: Es gibt keine Änderung seit dem letzten Commit, oder der Ordner ist (noch) kein Repository (2.2).
  • Alles grün bei neuer Datei: Eine neue Datei hat keinen Vorgänger, deshalb ist jede Zeile „neu“.
  • Ganzer Absatz rot und grün, obwohl nur ein Wort neu ist: Git vergleicht zeilenweise. Ein langer Absatz ist eine Zeile. Das ist normal.
  • „Muss ich das alles lesen?“ Nein. Überfliegen, auf Überraschungen achten, im Zweifel Claude fragen: „Was hast du außer meiner Bitte noch geändert?“
  • Windows/Mac: Kein Unterschied in VS Code.

  • Offizielle Doku: https://git-scm.com/docs/git-diff

2.4 Commits

Dauer: ca. 5 Min.

Worum geht's

Ein Commit sichert einen guten Zwischenstand mit einer Nachricht, die erklärt, was sich geändert hat. Commit immer vor dem nächsten großen Auftrag an die KI: dann ist der Rückweg garantiert.

Lernziel

Nach diesem Thema können die Teilnehmenden …

  • einen Commit machen (selbst in VS Code oder durch Claude).
  • eine verständliche Commit-Nachricht formulieren.
  • sagen, wann ein Commit sinnvoll ist (nach jedem Stand, der gut ist; vor jedem Experiment).

So erklären wir es

  1. Das Bild: Quittung beim Einkaufen. Erst packst du den Korb (welche Änderungen kommen mit?), dann zahlst du und bekommst die Quittung mit Datum und Text. Der Korb heißt in Git Staging (Bereitstellen), die Quittung ist der Commit.

    Zwei Schritte: auswählen, was mitkommt, dann sichern. Meist willst du einfach alles mitnehmen.

  2. Gute Nachricht, schlechte Nachricht. Beispiel Wirtschaft (Budgetplaner):
    Schlecht Gut
    „Änderungen“ „Sparplan: Zinssatz auf 3 % korrigiert“
    „v2“ „Budget: Kategorie Reisen ergänzt“

    Die Nachricht schreibst du für dein späteres Ich. Sie beantwortet: Was ist jetzt anders? Ein Satz genügt.

  3. Wann committen? Wenn etwas gut ist, bevor etwas Neues beginnt. Faustregel: Würde es mich ärgern, diesen Stand zu verlieren? Dann committen.
  4. Zwei Wege. In VS Code: Quellcodeverwaltung, Nachricht ins Textfeld, Häkchen/„Commit“. Oder Claude bitten. Unser Tipp: Claude schreibt oft die bessere Nachricht, aber wir lesen sie vor dem Bestätigen.
  5. Was Git nicht tut: Es committet nie von allein. Auch Claude committet nur, wenn man es bittet.

Zeigen (Live-Demo)

Im Demo-Projekt liegt noch die Änderung aus 2.3 (Abschnitt „Wetter-Alternativen“). Erst in VS Code:

  1. Quellcodeverwaltung öffnen, Datei(en) mit „+“ bereitstellen.
  2. Nachricht tippen: Törnplan: Wetter-Alternativen ergänzt.
  3. Commit klicken.

Dann das Gleiche per Claude, mit einer neuen kleinen Änderung:

Committe den aktuellen Stand mit einer passenden Nachricht auf Deutsch. Zeig mir die Nachricht, bevor du committest.

Zum Schluss git log --oneline (oder die Verlaufs-Ansicht): Beide Commits stehen untereinander, jüngster oben.

Selbst machen (Übung)

  1. Hast du seit dem Start etwas Gutes erstellt? Dann:
    Committe den aktuellen Stand mit einer passenden Nachricht.
  2. Frag: „Zeig mir den Verlauf der letzten Commits.“
  3. Geklappt, wenn dein Commit im Verlauf mit deiner Nachricht auftaucht. Das ist Teil des Meilensteins von Teil II.

Stolpersteine & Fragen

  • „Please tell me who you are“: Name/E-Mail fehlen, siehe 2.2.
  • Commit-Knopf grau / „Nothing to commit“: Keine Änderungen, oder nichts bereitgestellt.
  • Editor geht auf (vim) im Terminal: Passiert bei git commit ohne -m, wenn Git keinen Editor eingestellt hat. Das verwirrt Anfänger. Vorbeugen: git config --global core.editor "code --wait" (schon in 1.2), dann öffnet sich VS Code (Stand 2026-11, [KB] 24, §Install and one-time setup). Falls es doch passiert: Fenster schließen, neu versuchen oder Claude fragen.
  • Im Verlauf steht Co-Authored-By: Claude …: Claude hängt standardmäßig eine Zeile Co-Authored-By: <Modellname> <noreply@anthropic.com> an seine Commit-Nachrichten. Das ist gewollt und ehrlich (wer hat mitgeschrieben). Man sieht sie in git log. Abschaltbar über die Einstellung attribution (Stand 2026-11, [KB] 24, §In Claude Code).
  • „Wie oft?“ Lieber öfter. Kleine Commits sind leichter zu verstehen und rückgängig zu machen.
  • Sind committete Dateien gesichert? Nur auf diesem Rechner. Gegen Festplattendefekt hilft erst ein Online-Backup (2.9).

2.5 Branches

Dauer: ca. 8 Min.

Worum geht's

Ein Branch ist eine Abzweigung, auf der man eine Alternative ausprobiert, während das Hauptprojekt unberührt bleibt. Gefällt das Experiment, führt man es zurück; gefällt es nicht, wirft man den Branch weg. Kein Pflichtthema: Wer wenig Zeit hat, zeigt es nur als Demo.

Lernziel

Nach diesem Thema können die Teilnehmenden …

  • erklären, wozu ein Branch gut ist (Alternative ausprobieren, ohne main zu gefährden).
  • Claude bitten, einen Branch anzulegen und dorthin zu wechseln.
  • erkennen, auf welchem Branch sie gerade sind.

So erklären wir es

  1. Das Bild: Wegverzweigung auf der Wanderung. Du stehst am Wegweiser und willst wissen, ob der Seitenweg zur Hütte besser ist. Du gehst ihn testen. Ist er schlecht, gehst du zurück zum Wegweiser, und die Hauptroute ist unverändert.
    main        ●────●────●────────────●   ← bleibt, wie es war
                  \
alternative        ●────●             ← hier wird ausprobiert
  2. Beispiel Reisen: Der Reiseplan für Island liegt als Hauptversion vor. Idee: „Was, wenn wir statt Mietwagen nur Bus und Bahn nehmen?“ Auf einem Branch ohne-auto lässt Claude den ganzen Plan umbauen. Der Original-Plan auf main bleibt unberührt.
  3. Der Hauptzweig heißt main (in manchen Installationen master). Das ist „die echte Version“.
  4. Zusammenführen heißt Merge. Gefällt die Alternative, holen wir sie in main. Das zeigen wir nur, wenn Zeit ist, und lassen es Claude erledigen. Bei Textdateien gibt es selten Konflikte, die wir hier nicht vertiefen.
  5. Unterschied zu Commits: Commits sind die Punkte auf der Zeitleiste. Ein Branch ist eine zweite Zeitleiste daneben.
  6. Einordnung: Für viele Einsteiger reicht ein einziger Branch plus Commits. Branches sind das „fortgeschrittene Werkzeug“, das wir kurz zeigen, damit der Begriff nicht fremd ist.

Zeigen (Live-Demo)

Demo-Projekt Segeltörn-Planer, alles committet:

Leg einen neuen Branch „alternative-route“ an und wechsle dorthin. Zeig mir danach, auf welchem Branch ich bin.

Dann:

Plane die Route komplett um: statt Kroatien segeln wir von Mallorca aus. Passe toernplan.md an.

Committen lassen. Dann zurück:

Wechsle zurück auf main.

Wir öffnen toernplan.md: Die Datei ist wieder wie vorher. Dann wieder auf den Branch wechseln: Die Mallorca-Version ist da. Auf den Moment des Zurückspringens achten: Die Datei verändert sich im Editor, ohne dass jemand tippt. Das ist der Aha-Effekt.

Optional: In VS Code zeigt die untere Statusleiste links den Branch-Namen.

Selbst machen (Übung)

Nur wenn Zeit ist (sonst ausfallen lassen):

  1. „Leg einen Branch experiment an und wechsle dorthin.“
  2. Eine mutige Änderung machen lassen (z. B. Gliederung komplett umstellen), committen.
  3. „Wechsle zurück auf main.“ Ist die Datei wie vorher?
  4. Geklappt, wenn sich der Inhalt beim Wechsel mit ändert.

Stolpersteine & Fragen

  • Wechseln mit nicht committeten Änderungen: Git kann sich weigern oder nimmt die Änderungen mit. Regel: Erst committen, dann wechseln (2.4).
  • „Auf welchem Branch bin ich?“ Statusleiste in VS Code, oder Claude fragen.
  • Merge-Konflikt: Selten bei einer Person. Wenn es passiert: Claude bitten, den Konflikt zu erklären und aufzulösen, und das Ergebnis prüfen.
  • „Wozu brauche ich das allein?“ Für große Experimente mit KI: „Mach es völlig anders“ passiert auf einem Branch, main bleibt sicher. Alternativ reicht auch ein Commit davor (2.6).
  • Branch löschen: Per Claude bitten. Erst sicherstellen, dass nichts Wichtiges darauf liegt.

  • Kollegen-Folien: nichts Passendes.
  • Offizielle Doku: https://git-scm.com/book/de/v2/Git-Branching-Branches-auf-einen-Blick

2.6 Fehler rückgängig machen

Dauer: ca. 10 Min.

Worum geht's

Das ist der Höhepunkt von Teil II. Claude macht etwas Unerwünschtes, und wir holen den alten Stand in Sekunden zurück. Mit einem verlässlichen Weg zurück kann man viel mutiger experimentieren. Hier entsteht der Aha-Moment.

Lernziel

Nach diesem Thema können die Teilnehmenden …

  • vor einem riskanten Auftrag committen.
  • eine nicht gewollte Änderung per Prompt zurücknehmen lassen.
  • den Unterschied kennen: noch nicht committete Änderungen verwerfen vs. einen alten Commit rückgängig machen.

So erklären wir es

  1. Das Bild: Ski-Piste mit Sicherheitsnetz. Auf der Buckelpiste fährst du nur mutig, wenn du weißt, dass du nicht ins Leere fällst. Git ist das Netz.
  2. Der Ablauf in vier Schritten (an die Tafel, so merken sich das alle):
    1. Committen        → Stand sichern
2. Claude wagen     → große, mutige Änderung
3. Diff ansehen     → gefällt es?
4. Nein → zurück    → alter Stand ist wieder da
  3. Zwei Fälle.
    • Noch nicht committet: „Verwirf meine letzten Änderungen an dieser Datei.“ Achtung: Das ist endgültig. Was nie committet wurde, kann Git nicht zurückholen.
    • Schon committet: Ein früherer Commit lässt sich rückgängig machen (im Fachwort revert), der Verlauf bleibt erhalten.

      Deshalb die Regel Nr. 1: erst committen, dann wagen. Dann ist der Rückweg immer da.

  4. Zweiter, schneller Weg: Rückspulen in Claude. Esc Esc bei leerem Eingabefeld oder /rewind (auch /undo) öffnet eine Liste der bisherigen Aufträge. Man wählt einen aus und stellt Code und/oder Gespräch auf den Stand davor zurück. Praktisch für „das eben war Quatsch“. Grenze: Dateien, die nur durch Shell-Befehle verändert wurden, und die meisten Änderungen durch Unter-Agenten werden nicht zurückgespult. Git bleibt das eigentliche Sicherheitsnetz (Stand 2026-11, [KB] 25, §Control while it works) und [KB] 11, §6. Checkpoints and rewind).
  5. Warum das mit KI so wichtig ist. Ein Agent kann hundert Dinge auf einmal ändern. Ohne Netz muss man alles einzeln prüfen. Mit Netz probiert man: „Mach es völlig anders“, und wenn es schlechter ist, zurück.
  6. Haltung: Rückgängig machen ist kein Versagen, sondern Teil der Methode. Gute Maker verwerfen oft.

Zeigen (Live-Demo)

Unsere Lieblings-Demo (curriculum.md). Mit dem Segeltörn-Planer (Visualisierung der Route, vorher einmal komplett durchspielen):

  1. Zustand gut, committen:
    Committe den aktuellen Stand mit der Nachricht „Routen-Karte funktioniert“.
  2. Absichtlich verschlimmbessern:
    Mach die Routen-Karte völlig anders: dunkles Design, neonfarben, alle Beschriftungen auf Latein, Etappen als Kreisdiagramm.
  3. Im Browser ansehen. Das Publikum lachen lassen. Dann Diff ansehen (2.3): Wie viel hat sich geändert?
  4. Zurückholen:
    Gefällt mir nicht. Stell den Stand vom letzten Commit wieder her.
  5. Browser neu laden: Die alte Karte ist da.

Wir sagen dazu laut: „Das hat 10 Sekunden gedauert. Die KI durfte alles umbauen, und wir haben nichts riskiert.“ Claude fragt vor dem Zurücksetzen nach Erlaubnis. Wir lesen die Anfrage gemeinsam vor, damit klar ist, dass das Verwerfen endgültig ist. Diese Demo im Manual-Modus zeigen (1.4): Der Auto-Modus blockiert git reset --hard und git clean -fd standardmäßig, die Demo liefe dort ins Leere (Stand 2026-11, [KB] 24, §In Claude Code).

Zweite, kurze Variante für Fortgeschrittene: einen schon committeten schlechten Stand zeigen und „Mach den letzten Commit rückgängig“ sagen.

Selbst machen (Übung)

Aus dem Handout („Mutig verschlimmbessern“):

  1. Committe deinen aktuellen Stand.
  2. Bitte Claude: „Schreib ueber-mich.md komplett um, im Stil eines Piraten.“ (Oder eine eigene Datei: „im Stil eines Wetterberichts“, „als Börsenbericht“.)
  3. Sieh dir den Diff an. Gefällt dir das?
  4. Nein? „Stell den Stand vom letzten Commit wieder her.“
  5. Geklappt, wenn die Datei wieder aussieht wie vor Schritt 2. Dann ist der Meilenstein von Teil II erreicht.

Schnelle Teilnehmende: Im Schritt 4 selbst entscheiden, ob sie lieber behalten und committen.

Stolpersteine & Fragen

  • Ohne vorherigen Commit: Die Übung funktioniert nicht, es gibt nichts, wohin man zurückkann. Wir erinnern in Schritt 1 ausdrücklich.
  • Neue Dateien: Hat Claude eine ganz neue, nie committete Datei angelegt, entfernt „Stand wiederherstellen“ sie unter Umständen nicht. Claude bitten: „Lösch auch die neu angelegten Dateien.“ (vor dem Workshop in der Demo ausprobieren, welcher Prompt zuverlässig ist).
  • Rückspulen (/rewind) hat eine Datei nicht zurückgesetzt: Wurde sie per Shell-Befehl geändert (z. B. mv, sed), kennt Claude den alten Stand nicht. Dann hilft nur Git.
  • Sicher verwerfen statt löschen: git stash legt nicht committete Änderungen beiseite, statt sie endgültig zu vernichten, und holt sie mit git stash pop zurück (Stand 2026-11, [KB] 24, §Stash). Gute Alternative zu „verwerfen“, wenn man unsicher ist.
  • Browser zeigt noch alten/neuen Stand: Seite neu laden.
  • „Ist die schlechte Version dann weg?“ Wenn sie nie committet wurde: ja, endgültig. Das ist ok, wir wollten sie ja nicht.
  • „Kann ich auch auf einen Commit von letzter Woche zurück?“ Ja: „Zeig mir den Verlauf und stell die Datei auf den Stand von Commit X zurück.“ Details bei 2.8.

  • Handout: Schüler-Seite (Übung „Mutig verschlimmbessern“)
  • Kollegen-Folien: nichts Passendes. Vertrauen und Prüfen: [CW] S. 9 (siehe 4.5).
  • Offizielle Doku: https://git-scm.com/book/de/v2/Git-Grundlagen-Änderungen-rückgängig-machen

2.7 .gitignore

Dauer: ca. 5 Min.

Worum geht's

Die Datei .gitignore ist eine Liste: Was hier steht, beobachtet Git nicht. Große Daten, Erzeugtes und Vertrauliches gehören nicht in den Verlauf. Was einmal committet ist, bleibt nämlich im Verlauf, auch wenn man die Datei später löscht.

Lernziel

Nach diesem Thema können die Teilnehmenden …

  • sagen, was nicht in ein Repository gehört (Passwörter, Schlüssel, große Dateien, Erzeugtes).
  • Claude bitten, eine .gitignore anzulegen.
  • prüfen, ob eine Datei ignoriert wird.

So erklären wir es

  1. Das Bild: Packliste für die Hüttentour. Du nimmst den Rucksack, aber nicht den Kühlschrank mit. Die .gitignore ist die Liste „bleibt zu Hause“.
  2. Was kommt rauf? Drei Gruppen, mit Beispiel aus den Bergen:
    • Zu groß: die 2 GB Videos und GPX-Rohdaten der Tour. Git ist für Text gemacht, nicht für Filme.
    • Erzeugt: Dateien, die der Agent jederzeit neu bauen kann (Zwischenergebnisse, tmp/, Ordner wie node_modules/). Man sichert das Rezept, nicht den Kuchen.
    • Vertraulich: Passwörter, Zugangsschlüssel (oft in einer Datei .env), persönliche Daten, Unterlagen, die niemand sehen soll. Dazu O.3 Passwörter und O.1 Datenschutz.
  3. Die Falle. Alles Committete bleibt im Verlauf, auch nach dem Löschen. Wer ein Passwort committet und das später merkt, muss es als „verbrannt“ ansehen und ändern. Darum: .gitignore vor dem ersten Commit.

    Merksatz: Erst auf die Liste, dann committen.

  4. Wie sieht sie aus? Eine Textdatei, eine Zeile pro Muster:
    .env
tmp/
*.mp4
.DS_Store
    Wir erklären nur die Idee (Ordner mit /, * steht für „beliebig“), nicht die ganze Syntax. Claude schreibt sie.
  5. Hinweis: Ignorieren hilft nur bei Dateien, die Git noch nicht kennt. Bei schon committeten braucht es zusätzliche Schritte, die Claude erledigen kann.

Zeigen (Live-Demo)

Im Demo-Projekt eine Datei .env mit Fake-Inhalt (WETTER_API_KEY=nicht-echt) und einen Ordner tmp/ anlegen. In der Quellcodeverwaltung erscheinen beide als neu. Dann:

Leg eine .gitignore an, die den Ordner tmp/, die Datei .env und alle .mp4-Dateien ausschließt.

Quellcodeverwaltung: .env und tmp/ sind verschwunden, dafür taucht .gitignore selbst als neu auf (die gehört mit in den Commit). Frage ans Publikum: „Wo wäre das Passwort gelandet, wenn wir es nicht ignoriert hätten?“ (Im Verlauf, für immer.)

Selbst machen (Übung)

  1. Überlege: Gibt es in deinem Projekt etwas, das nicht in den Verlauf gehört (große PDFs, Fotos, Privates)?
  2. Leg eine .gitignore an, die große PDFs und den Ordner tmp/ ausschließt.
  3. Geklappt, wenn die ausgeschlossenen Dateien nicht mehr in der Quellcodeverwaltung auftauchen. Dann .gitignore committen.

Stolpersteine & Fragen

  • Datei taucht trotzdem auf: War sie schon committet, oder das Muster passt nicht. Claude fragen: „Warum wird X nicht ignoriert?“
  • Versteckte Datei: .gitignore beginnt mit Punkt, Mac-Finder zeigt sie nicht (Cmd + Shift + .), VS Code schon.
  • „Ich habe ein Passwort committet.“ Passwort sofort ändern. Das Löschen aus dem Verlauf ist aufwendig, ändern ist der sichere Weg.
  • Große Dateien trotzdem sichern? Separat sichern, z. B. Cloud-Speicher oder externe Platte (O.4).
  • Schlägt Claude selbst Vertrauliches vor? Gute Frage an ihn: „Gibt es in diesem Ordner Dateien, die ich besser nicht committen sollte?“

Material & Quellen

  • Kollegen-Folien: nichts Passendes.
  • Offizielle Doku: https://git-scm.com/docs/gitignore

2.8 Git + Claude Code

Dauer: ca. 5 Min.

Worum geht's

Man muss kaum Git-Befehle lernen: Claude kennt sie. Du sagst, was du willst („erklär mir den Verlauf“, „bereite einen Commit vor“), Claude übersetzt in Git und du prüfst das Ergebnis. Das schließt Teil II ab.

Lernziel

Nach diesem Thema können die Teilnehmenden …

  • Claude den Projektverlauf erklären lassen.
  • Commits von Claude vorbereiten lassen und die Nachricht prüfen.
  • gezielt einen alten Stand einer Datei erfragen.

So erklären wir es

  1. Das Bild: Chronist. Claude liest den Verlauf wie ein Historiker die Chronik und erzählt ihn in normalen Sätzen. Beispiel Physik: Ein Semester Laborprotokolle, 30 Commits. „Was habe ich im Oktober an der Auswertung geändert?“ Statt durch 30 Einträge zu klicken, fragen wir.
  2. Drei Dinge, die gut klappen:
    • Verlauf erklären: „Fasse die letzten zehn Commits zusammen.“
    • Commit vorbereiten: Claude schaut den Diff, schlägt eine Nachricht vor, committet nach Bestätigung.
    • Alten Stand holen: „Wie sah toernplan.md vor drei Commits aus?“
  3. Wir bleiben Pilot. Im Manual-Modus fragt Claude vor Befehlen um Erlaubnis, im Auto-Modus prüft ein zweites Modell und blockiert z. B. git reset --hard und Force-Push (1.7 Berechtigungen). Bei Git-Befehlen, die etwas verwerfen oder umschreiben, lesen wir genau mit.

    Faustregel: Anschauen darf Claude einfach. Bei allem, was Dinge verwirft oder umschreibt, schauen wir genau hin.

  4. Gute Arbeitsroutine (das nehmen wir mit in Teil IV): Commit → Auftrag → Diff prüfen → Commit. So entsteht ein sauberer Verlauf, an dem man später (und Claude auch) nachvollziehen kann, was passiert ist.
  5. Kurzer Hinweis: Im Claude-Code-Terminal führt ein vorangestelltes ! einen Shell-Befehl direkt aus (z. B. ! git status). Das läuft sofort, ohne Abfrage, und die Ausgabe landet im Gespräch, Claude liest sie mit (Stand 2026-11, [KB] 25, §Input). Praktisch, aber für Anfänger nicht nötig. Weil keine Abfrage kommt: nur Befehle, die man versteht.

Zeigen (Live-Demo)

Im Demo-Projekt mit mehreren Commits aus den vorherigen Themen:

Erkläre mir den Verlauf dieses Projekts in einfachen Worten. Was ist wann passiert?

Dann eine kleine Änderung machen lassen und:

Schau dir meine Änderungen an und schlag mir eine Commit-Nachricht vor. Committe erst, wenn ich ja sage.

Wir lesen den Vorschlag gemeinsam: Passt er zur Änderung? Dann „ja“. Zum Schluss:

Wie sah toernplan.md vor zwei Commits aus? Zeig mir den Unterschied zu heute.

Selbst machen (Übung)

  1. Frage Claude nach dem Verlauf deines Projekts.
  2. Lass eine kleine Änderung machen und bitte um eine Commit-Nachricht zur Prüfung. Bestätige oder verbessere sie.
  3. Geklappt, wenn dein neuer Commit mit einer Nachricht im Verlauf steht, die du verstehst.

Stolpersteine & Fragen

  • Claude committet ungefragt? Nur, wenn man darum bittet. Wer Kontrolle will, schreibt „Committe erst, wenn ich ja sage.“
  • Nachricht auf Englisch/zu lang: Sagen, was man will: „Auf Deutsch, höchstens eine Zeile.“
  • Alles in einem riesigen Commit: Besser öfter committen (2.4), sonst erklärt auch Claude nur Chaos.
  • Verlauf wirkt leer: Es gab noch keine Commits, oder der Ordner ist kein Repository (2.2).
  • „Soll ich Git überhaupt selbst können?“ Ein Grundverständnis (Commit, Diff, zurück) reicht. Die Befehle liefert Claude.
